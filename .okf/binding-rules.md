# Metal binding rules

Authority: `docs/superpowers/specs/2026-09-12-ext-metal-0.8.0-design.md` §4–§5
(this file restates that spec's rules as living law; the spec itself is the
binding authority if the two ever disagree).

## Inherited wholesale

ext-appkit's `.okf/binding-rules.md` and `toolchain.md` apply to ext-metal
without change:

- **One ext call = one Objective-C message send.** The only sanctioned
  composite is `alloc`+`init` construction glue.
- `@zep` annotations in `src/*.h` are the single source of truth; everything
  under `metal/` (zep) and `optimizers/` is generated by `scripts/gen-zep.php`
  and never hand-edited.
- Nothing silently omitted: unbindable members (blocks, `NSCoder`,
  `NSAttributedString`, …) stay as commented `@reserved` signatures; audit
  requires bound + reserved (+ construct) to equal the SDK header's member
  count per type. Carve-out while a type is still partial: `@audit partial`
  sanctions bound+reserved falling short of that count with no itemization
  required yet; only once a type graduates to fully-bound must every
  remaining unbindable member appear as `@reserved` so bound+reserved equals
  the header count exactly (see
  [traps/blocks-reserved.md](/traps/blocks-reserved.md)).
- Type table: BOOL/NSInteger/NSUInteger/CGFloat/float → bool/int/int/double/
  double; NSString → string (nullable → `var`); enums (incl. NS_OPTIONS) →
  int; objects → int handles; structs → component scalars in, assoc array
  out.
- **A handle carries no type, so every binding checks its own receiver
  and object arguments**: `MTL_ARG_AS` (`isKindOfClass:`) for classes,
  `MTL_ARG_PROTO` (`conformsToProtocol:`) for protocols, both in
  `src/mtl-value.h`, both reading as nil on a mismatch. Skipping the check
  is not a "faithful pass-through" — it lets a wrong-type handle reach a
  selector the object does not implement, which aborts the process
  (see [bridge.md](/bridge.md)).
- Zephir reserved words and all-caps identifiers follow appkit's
  underscore/mixed-case rules.
- Constants and PHP enums live in **jovian/metal**, never in the ext.

Layering (verbatim house law, transposed): **ext-metal = Metal + unavoidable
glue; jovian/metal = PHP projection; venusian-metal = composition;
surface = abstraction.**

Class/file naming follows the appkit pattern:
`Metal\MTL\MTLDevice\MTLDevice` ↔ `metal/mtl/mtldevice/mtldevice.zep` ↔
`src/mtl-device.{h,m}`; QuartzCore types as
`Metal\QuartzCore\CAMetalLayer\CAMetalLayer` ↔ `src/ca-metallayer.{h,m}`.

## Amendment 1 — protocol audit

Metal's API objects are `@protocol`s (`MTLDevice`, `MTLCommandQueue`,
`MTLBuffer`, …) obtained from factories, never alloc'd. `audit-headers.php`
gains a protocol mode: it counts `@protocol` members from the Metal SDK
headers exactly as it counts `@interface` members for appkit.
Construction-path rule for protocols: a type is constructible when at least
one bound factory (a C function such as `MTLCreateSystemDefaultDevice`, or a
bound send on another type returning its handle, e.g. `newCommandQueue`)
produces it; the audit verifies this instead of demanding
`init*`/`@zep-construct`.

The marker grammar is `/*@audit factory <FQCN> <Producer>::<method> */`,
identical shape to `@zep`. Real example, `src/mtl-commandqueue.h`:

```c
/*@audit partial MTL\MTLCommandQueue slice zero: commandBuffer, label */
/*@audit factory MTL\MTLCommandQueue MTLDevice::newCommandQueue */
```

This tells the audit that `MTLCommandQueue` is constructible because
`MTLDevice::newCommandQueue` produces a handle of that class — no `init*`
or `@zep-construct` is required or expected on a protocol.

Semantics note (verified this session): an `@audit partial` type whose
`bound` count exactly equals its own header's block count audits **OK**,
not PARTIAL — the `partial` marker only changes if *more* members exist in
the SDK header than are accounted for. `MTLRenderPassColorAttachmentDescriptor`,
`MTLRenderPassColorAttachmentDescriptorArray`, and `CAMetalDrawable` are
`@audit partial` in source but print `OK` (see the worked-example table
below) because their slice-zero binding happens to be their whole header.

## Amendment 2 — C functions

Top-level Metal C functions (`MTLCreateSystemDefaultDevice`,
`MTLCopyAllDevices`; `MTLClearColorMake` excluded — it is a struct helper,
not a send) bind as static methods on their natural owner
(`MTLDevice::createSystemDefault()`), annotated `@zep` like any other
binding; one C call = one binding. `src/mtl-device.h`:

```c
/*@zep MTL\MTLDevice createSystemDefault() -> int */
zend_long mtl_mtldevice_create_system_default(void);
```

## Amendment 3 — the `NSError**` pattern

A selector with a trailing `error:` out-param binds under its full
flattened name (`newLibraryWithSourceOptionsError`, Wave A) and returns an
assoc array `{handle: int, error: int}` — exactly one of the two is
non-zero **whenever the send actually happened**; both are zero when the
binding refused to send at all (nil receiver, or an argument that did not
resolve to the required type). The error is an NSError registry handle
whose `localizedDescription` is readable via the Bridge. Without this amendment
Metal cannot compile a shader (the alternatives are block-based and
reserved). This pattern is available to future waves/extensions; appkit
may adopt it later but is not changed by this spec.

**Wave A form** (live): `MTLDevice::newLibraryWithSourceOptionsError` and
`MTLDevice::newRenderPipelineStateWithDescriptorError` both return
`{handle, error}`. `src/mtl-device.m` registers the `NSError *` only when
the call produced no object, so exactly one member is non-zero; both are
zero only when the call could not be made at all (nil receiver or
unresolvable argument, no send). `mtl_ret_handle_error` in
`src/mtl-value.h` is the one place that shape is built. Wave B adds the
third user, `MTLDevice::newComputePipelineStateWithFunctionError`, with no
change to the shape or to the helper.

Two consequences worth knowing:

- **A factory marker may name an `array`-returning producer.**
  `audit-headers.php` used to demand `-> int` from an `@audit factory`
  producer; the NSError** producers return `-> array`, so the check now
  accepts `int` *or* `array` (nothing else). Without this, `MTLLibrary`
  and `MTLRenderPipelineState` have no construction path at all.
- **MTLCompileOptions is deferred.** `newLibraryWithSource:options:error:`
  takes a nullable options object, and `0` is nil — enough to compile MSL
  from source, which is what Wave A needed. The class itself
  (`MTLLibrary.h`, 15 rw properties) is not bound; callers that need
  compile options wait for the wave that binds it.

**Slice-zero form of the pattern** (no shader compile yet, but the same
NSError shape is already exercised by `MTLCommandBuffer::error`):
instead of the `{handle, error}` assoc-array shape, a plain
`error(handle) -> int` accessor returns the NSError registry handle (0 =
none) after `commit`+`waitUntilCompleted`, and
`Bridge::errorDescription(handle)` reads its `localizedDescription`:

```c
/*@zep MTL\MTLCommandBuffer error(int handle) -> int */
zend_long mtl_mtlcommandbuffer_error(zval *handle);
```

The full `{handle, error}` return-array shape is reserved for Wave A's
`newLibraryWithSourceOptionsError` and friends, where the call itself can
fail to produce an object at all.

## Amendment 4 — cross-extension pointer seam

Every registry-handled type exposes Bridge glue
`Bridge::pointerOf(int handle): int` (raw pointer bits) and
`Bridge::adopt(string class, int pointerBits): int` (wrap a foreign pointer
into this extension's registry, retained). Raw pointer bits are the only
currency between extensions — never a registry handle from another
extension.

**Walk-through: CAMetalLayer → ext-appkit.** ext-metal owns `CAMetalLayer`;
ext-appkit owns `CALayer`/`NSView` (§7 of the spec, decision logged). To put
a Metal layer on an AppKit view:

1. `$layer = CAMetalLayer::init();` — metal's registry now holds it
   (`@zep-construct`, alloc+init glue).
2. `$ptr = Bridge::pointerOf($layer);` — metal hands out the raw pointer
   bits, not the handle.
3. ext-appkit's `Bridge::adopt('CAMetalLayer', $ptr)` wraps the same pointer into
   *its own* registry, retained — this is the named prerequisite (a small
   0.8.x ext-appkit point release) that `examples/proof_view.php` is
   written against; until it lands, `proof_view.php` exits 2 (SKIP).
4. ext-appkit calls `NSView::setWantsLayer`/`setLayer` with its own handle.

Each side owns one retain: metal's `init` retains once; appkit's `adopt`
retains again on the same pointer. Releasing on one side does not affect
the other's retain count — forgetting the release on whichever side is
done with the pointer leaks, but neither side may skip its own retain
under the assumption the other side "already did it".

`ext-metal` never links AppKit and never accepts appkit registry handles —
pointer bits only (see [traps/no-appkit-coupling.md](/traps/no-appkit-coupling.md)).

`audited=34 skipped=1 failures=0` → `AUDIT_OK`. `MTLCommandQueue=11` and
`MTLDevice=120` are the real SDK counts recovered by the Task 2 forward-decl
fix (a prior audit revision under-counted `MTLCommandQueue.h` as `header=0`
because `@protocol X;` forward declarations were mistaken for block
openers — fixed with a regression fixture; see
[traps/protocol-audit.md](/traps/protocol-audit.md)).

Wave A hit the *other* half of that same trap and fixed it: `sdkHeaderFor()`
resolved a companion type by scanning the framework's headers for the first
file mentioning `@interface`/`@protocol Class`, which also matches a bare
forward declaration. Metal forward-declares constantly and alphabetically
early — `MTLFunction` in `MTLComputeCommandEncoder.h`,
`MTLRenderPipelineState`/`MTLSamplerState` in `MTLArgumentEncoder.h`,
`MTLRenderCommandEncoder` in `MTLCommandBuffer.h` — so four Wave A types
would have been audited against `header=0` and failed. A candidate header
now only wins when `classBlocks()` finds a real block in it
(`scripts/tests/fixtures/Frameworks/Fake.framework/Headers/FakeAliases.h`
is the regression fixture; `audit-protocol.php` asserts `FakeQueue
header=4`).

Two Wave A rows to read carefully: `MTLBuffer` binds three calls against
one header member (`contents` backs both `contentsBytes` and
`setContentsBytes`), and `MTLRenderCommandEncoder`'s SDK selectors are
flattened house-style, so `setVertexBuffer:offset:atIndex:` binds as
`setVertexBufferOffsetAtIndex`.

**Flattening is not injective, and the tie-break is a suffix at bind
time.** `setVertexBufferOffset:atIndex:` (`MTLRenderCommandEncoder.h:157`)
flattens to exactly the same `setVertexBufferOffsetAtIndex` as the
selector Wave A bound; so do the `setFragmentBuffer`/
`setFragmentBufferOffset` pair and the `attributeStride` overloads. That
is the appkit collision case (`drawKnob`/`drawKnobRect`,
`postNotificationNameObject`/`...UserInfo`), and the house resolution is
the same here: the first binding keeps the plain flattened name, and
whichever colliding selector a later wave binds takes a distinguishing
suffix chosen at bind time. Nothing is "reserved" by binding one of them
first — the collision is simply not resolved until the second one is
bound.

**Wave B hits that same collision a second time, and resolves it the same
way.** `MTLComputeCommandEncoder.h` declares both
`setBuffer:offset:atIndex:` (:66) and `setBufferOffset:atIndex:` (:72);
both flatten to `setBufferOffsetAtIndex`. Wave B binds the first, which
keeps the plain name; the second is unbound and un-reserved, and whichever
wave binds it picks the distinguishing suffix then. Three more Wave B rows
to read carefully: `MTLBlitCommandEncoder`'s two buffer↔texture copies are
nine-part selectors, so their flattened names
(`copyFromBufferSourceOffsetSourceBytesPerRowSourceBytesPerImageSourceSizeToTextureDestinationSliceDestinationLevelDestinationOrigin`
and its inverse) are long by construction, not by choice — their `options:`
overloads flatten to the same name plus `Options` and so do *not* collide;
`MTLComputePipelineState` lives in `MTLComputePipeline.h` and resolves via
the Wave A companion-header fix; and `MTLDevice`'s new
`newComputePipelineStateWithFunctionError` is the third user of Amendment
3 (only the plain overload binds — `options:reflection:` writes through an
out-parameter and the `completionHandler:` forms are blocks).

**Wave C rows.** `MTLRenderPipelineColorAttachmentDescriptor` reaches
18/18 — every property bound — and audits `OK` while still `@audit
partial` in source (the semantics note above). The depth/stencil
attachment descriptors bind `clearDepth`/`clearStencil` only; the resolve
filters (MSAA policy) are the unbound half of each 4-member header. Their
factory markers name `MTLRenderPassDescriptor::depthAttachment` /
`stencilAttachment`; inherited `texture`/`loadAction`/`storeAction` come
from `MTLRenderPassAttachmentDescriptor` (rule 10 — `MTL_ARG_AS` accepts
the subclasses). `clearDepth` is the first `-> double` return in the ext.

[toolchain.md](/toolchain.md) for the pipeline that produces these numbers.
